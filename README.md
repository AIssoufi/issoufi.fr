## 🚀 Getting Started

### Prerequisites

- [Node.js](https://nodejs.org/) 24 (see `.nvmrc`)
- [pnpm](https://pnpm.io/) 10.34.7, pinned by the `packageManager` field of `package.json`. Any recent pnpm switches to this version automatically inside the project.

### Installation

```bash
pnpm install
```

### Development

```bash
pnpm dev
```

The app will be available at [http://localhost:3000](http://localhost:3000), and opens in the browser unless `BROWSER=none` is set.

**Ports**: `pnpm dev` listens on 3000 and `pnpm preview` on Vite's default port, 4173, unless a `PORT` variable is set, in the environment or in `.env.local`. Then both use it, and so does the preview server of `pnpm test:browser`. Each Worktrunk worktree gets its own: when the worktree is created, `.config/wt.toml` writes `PORT=<port>` to its `.env.local` (gitignored), a port between 10000 and 19999 derived from the branch name, so it stays the same for the branch and several worktrees can serve the app at the same time. Read the port of a worktree in its `.env.local`, or override it for one run with `PORT=4000 pnpm dev`. An empty or invalid `PORT` is ignored (`vite/utils.ts`). When the port is taken, `pnpm dev` and `pnpm preview` stop with an error instead of moving to another port (`strictPort`), so a test never reaches the server of another worktree by mistake: stop the server that holds the port, or pick another one with `PORT`.

### Production

```bash
pnpm build     # Type-check, then build to dist/
pnpm build:standalone   # Type-check, then build the site that opens from the disk to dist-standalone/ (see Releases)
pnpm size      # Check the size of dist/ (run it after pnpm build)
pnpm preview   # Serve the production build locally
pnpm smoke-test [site URL]   # Check that a deployed site, production by default, serves the pages, robots.txt and sitemap.xml of dist/
```

`pnpm size` fails when the scripts and style sheets that the home page loads before it renders (those that `dist/index.html` references with `<script src>`, `modulepreload` or `stylesheet`) exceed 150 kB gzip, or when those of the whole build, every chunk included, exceed 210 kB gzip. It also fails when `dist/index.html` references none, and warns about any other file of the build over 500 kB, such as an image or the CV. These limits are in `scripts/ci/constants.mjs`.

`pnpm smoke-test [site URL]` requests every page of `dist/` on the site, those of its language folders included (`en/projects.html` at `/en/projects`), plus an unknown path in each folder that has a `404.html` (`/smoke-test-page-that-does-not-exist` and `/en/smoke-test-page-that-does-not-exist`), and fails unless each answers with the expected status (200, or 404 for the unknown paths) and the title and canonical URL of the build. It also requests `/robots.txt` and `/sitemap.xml` (`SERVED_AS_BUILT_FILES` in `scripts/ci/constants.mjs`), and fails unless each answers with a 200 and the exact content of the build. The English pages and the English not found page have titles of their own, so a server that sent the French file for an English URL fails. It retries for about 20 seconds while a new deployment spreads, and fails at once when `dist/` is missing or holds no HTML page. Without a URL, it checks the production site, `SITE_URL` in `scripts/ci/constants.mjs`, while an empty URL, such as an unset deployment URL, fails rather than checking production.

### Link preview image

```bash
pnpm exec playwright install --only-shell chromium   # Once, and after a Playwright update
pnpm og-image        # Regenerate public/og-image.jpg and public/og-image-en.jpg
```

`public/og-image.jpg` is the 1200×630 image that link previews show for every French page, and `public/og-image-en.jpg` its English version, shown for the pages under `/en/` (`OG_IMAGE_PATHS` in `src/utils/pages.ts`, which fills the `%PAGE_IMAGE_URL%` placeholder of `og:image` in `index.html`). `pnpm og-image` (`scripts/og-image/generate-og-image.mjs`) regenerates both from the repository alone: the texts of the home page in each language (`src/i18n/fr.ts` and `en.ts`, `TRANSLATION_MODULES` in `scripts/utils/constants.mjs`), the design tokens (`src/theme/theme.ts`), the background photo and the particle field of the home page, and the domain of `SITE_URL` (`src/utils/pages.ts`), which it reads through Vite. Chromium, from Playwright, renders the page that the script builds for each language in the web fonts of the site, whose files it reads from `public/fonts/` (see Fonts in Conventions), so it needs no network, and it stops when a text of a language, a design token or a particle setting is missing, or when a font does not load in one of the weights the page uses. Each screenshot is saved as a JPEG of quality 90 (`OG_IMAGE_JPEG_QUALITY`), about 100 kB where a PNG of the same image weighs 470 kB, and the script fails rather than write an image over 300 kB, above which WhatsApp shows no image: it writes the images only once all of them are drawn, so a failure leaves both unchanged. The particles are drawn from a fixed seed (`PARTICLE_SEED`), so two runs on the same machine write the same files. The sizes and spacing of the layout are in `scripts/og-image/constants.mjs`.

Run it after changing the texts, the background photo, the colors or the fonts of the home page, look at both images, then commit them with the change: it runs on demand, not in the build or the CI.

### CV

```bash
pnpm exec playwright install --only-shell chromium   # Once, and after a Playwright update
pnpm cv              # Generate public/CV - Adam Issoufi.pdf and public/CV - Adam Issoufi (EN).pdf
```

The CV button of each language downloads the CV written in it: `public/CV - Adam Issoufi.pdf` on the French pages, `public/CV - Adam Issoufi (EN).pdf` on the English ones (`CV_URLS` in `src/App/Header/CvLink/constants.ts`). `pnpm cv` (`scripts/cv/generate-cv.mjs`) generates both from the content of the site, which it reads through Vite, so that the CV says what the site says: the name and the job title of the home page, the experiences of the Experiences page (`src/pages/Experiences/.data/experiences.json` and the `exp` translations), and the freelance and personal projects of the Projects page. What the site does not show, the contact details, the skills and the education, is in `scripts/cv/.data/cv.json`, which the site owner keeps up to date, in both languages. Chromium, from Playwright, prints each CV as a tagged A4 PDF of at most two pages, in the font and the colors of the site, with its text selectable and searchable and its links clickable. The font is Montserrat, the body font of the site, from the static TrueType files of `scripts/cv/fonts/` (regular, medium and bold, `CV_FONT_FILES` in `scripts/cv/constants.mjs`), which Chromium embeds as TrueType fonts: a variable font, such as the one that browsers load for the site, would become Type 3 fonts, whose text Preview and Safari can neither select nor search. The README of that folder gives their source, their hashes and their license, `OFL.txt`, which must stay next to them; the folder is outside `public/`, so neither `dist/` nor the release archive holds it. The script needs no network, and it stops when a text is missing, when a font does not load, or when the PDF, read back with pdf.js (the PDF library of Firefox), holds a Type 3 font or another font than the one of the site, lacks a text or a link of the site, has more than two pages or weighs over 500 kB. It writes the PDFs only once both are right, with the fingerprint of the content of each one (`scripts/cv/fingerprints.json`). The print sizes are in `scripts/cv/constants.mjs`.

Run it after changing a text or a data file that the CV reads, look at both PDFs, then commit them with the fingerprints: `scripts/cv/cvs.spec.js` fails while the content of the site no longer gives the fingerprint of a CV, or while a CV of `public/` lacks a text or a link of the site.

### Tests

```bash
pnpm test            # Single run
pnpm test:watch      # Watch mode
pnpm test:coverage   # Single run with coverage, HTML report in coverage/index.html
```

Tests are `*.spec.jsx` (components), `*.spec.ts` (helpers and hooks, those of `e2e/` included) and `*.spec.js` (helpers of the scripts of `scripts/` and the test helpers of `src/styleTestUtils.js`, `src/pages/testUtils.js`, `src/App/testUtils.js` and `src/theme/testUtils.js`, and `scripts/cv/cvs.spec.js`, which checks the CVs of `public/`) files next to the code they test. Every component has one. `vite.config.spec.ts` builds the site in memory, with the real config, and checks the generated pages, the sitemap and `_headers`, and `vite.standalone.config.spec.ts` does the same for the standalone build (see Releases). `src/setupTests.ts` renders every component in the theme and global styles of the app (`src/testUtils.tsx`), so the styles hold the values of the tokens, gives no canvas context, as jsdom has none, and fails a test that logs an error with `console.error`, such as a React warning, so the output stays clean. A patch of `@asamuzakjp/dom-selector`, the selector engine of jsdom (`patches/`, declared under `patchedDependencies` in `pnpm-workspace.yaml`), gives `:focus-visible` to an element reached with Tab during its focus event, which jsdom refuses after the first Tab of a test file: remove it once a release that jsdom uses fixes the bug ([ISF-173](https://github.com/AIssoufi/issoufi.fr/issues/173)). As in production, styled-components inserts its rules into the CSSOM (`SC_DISABLE_SPEEDY` in `vite.config.ts`), which keeps jsdom from parsing a whole `<style>` again on every change, and `src/setupTests.ts` fails a test whose component inserts a rule that browsers would drop, such as one holding the source of a function interpolated outside a `css` block. The tests read the declared styles through the CSSOM (`listStyleRules`, `declaredStyle` and `serializeCssValue` of `src/styleTestUtils.js`), since jsdom ignores media queries and pseudo-elements. jsdom has no `matchMedia` either: a spec that needs a media query to match, such as the reduced motion preference, stubs it with `stubMatchMedia` (`src/mediaQueryTestUtils.ts`), whose `setMatches` changes the result as a resize or a change of the system settings would. `pnpm test:coverage` fails when the coverage of `src/`, of the Vite config helpers (`vite/`), of the browser test helpers (`e2e/`) and of the script helpers (`scripts/utils/`, `scripts/ci/utils/`, `scripts/og-image/utils/` and `scripts/cv/utils/`) drops below the thresholds of `vite.config.ts` (`COVERAGE_THRESHOLDS_PERCENT`).

### Browser tests

```bash
pnpm exec playwright install --only-shell chromium   # Once, and after a Playwright update
pnpm build
pnpm test:browser    # Check in Chromium that no page of the build scrolls sideways or requests Google, that the timeline dots sit on its line, that each page is served at its URL in each language (`/en/…`), that the CV button and the GitHub icon sit centered under the language toggle, the icon under the CV button of the mobile menu, and that no content passes under them, that the tooltip of the CV button shows whole next to it, that the project cards fill the width of their section with the same size and columns, in "Show all" and on the last page of the row, that the arrows show every project in turn, that nothing moves with reduced motion, that the header stays on the screen down to the end of the long pages, under a blurred band of its height, compact on a short screen, that the open mobile menu shows each of its links whole on a phone held sideways, scrolls when higher than the screen, keeps the page behind it still and the language toggle usable above it, and that the error pages center their message over a background photo
```

jsdom computes no layout, so the browser tests run in a real browser with [Playwright](https://playwright.dev/): the `*.e2e.ts` files of `e2e/`, configured by `playwright.config.ts`. They test the production build: `pnpm test:browser` serves `dist/` with `pnpm preview` on the port of the worktree (see Ports), with `--strictPort`, and never reuses a server already on that port, so run `pnpm build` first. `e2e/horizontal-overflow.e2e.ts` opens every route of `PAGES` (`src/utils/pages.ts`), so a new page is covered without changing it, and two unknown paths for the not found page, the second one longer than a phone screen (`LONG_NOT_FOUND_ROUTE`: percent-encoded words, which the page names decoded, then a word of 64 letters, which it wraps), at the URLs of each language of `LANGUAGES` (`src/i18n/constants.ts`), `/projects` and `/en/projects`, on screens 320, 375, 414 and 1440 px wide (`e2e/constants.ts`). A page fails when it is wider than the screen (`document.documentElement.scrollWidth` above its `clientWidth`), and its screenshot is saved in `test-results/`.

`e2e/google-requests.e2e.ts` opens the same routes in each language, but the long unknown path, records every request of the page, and fails when one goes to a host of Google: the domains of `GOOGLE_DOMAINS` and their subdomains, such as `fonts.googleapis.com` and `fonts.gstatic.com`, and the country domains of the search engine (`isGoogleHost` and `isGoogleUrl`, `e2e/utils.ts`). It also fails unless each font of `FONT_FACES` (`src/theme/constants.ts`) is loaded once the page is shown, from the files of the site.

`e2e/timeline.e2e.ts` checks, in the same languages and at the same widths, that the dots of the Experiences timeline sit on its line: the mobile layout draws a dot for each company and each later role, the desktop layout one in each period column. The line and the dots are `::before` and `::after` pseudo-elements placed by hand, whose offset depends on the size, the border and the `box-sizing` of the dots, and the DOM gives no box for a pseudo-element. The test measures them through the DevTools protocol (`DOM.getBoxModel`, CSS transforms included, `e2e/pseudo-elements.ts`), and fails when the center of a dot is more than 0.5 px from the center of the line (`MAX_DOT_OFFSET_PX`), when it finds no dot, or when it does not find exactly one line. It finds them by stable attributes rather than by the DOM structure: `data-timeline-line` on the timeline and `data-timeline-dot` on each element that draws a dot, whose value names the pseudo-element that draws it (`before` or `after`). When a line or a dot moves to the other pseudo-element, change its attribute with it.

`e2e/language.e2e.ts` opens every page at its URL in each language and fails unless the server sends the HTML file of that language: its canonical URL, which the app never changes, its `x-default` alternate link and its `lang`. It also checks that the root opens at `/en/` once English was stored, and that the toggle moves `/projects` to `/en/projects`, in English, which a reload keeps.

`e2e/github-link.e2e.ts` checks the CV button and the GitHub icon. At 800 px (the tablet breakpoint), 1280, 1440 and 1920 px wide (`FLOATING_CONTROLS_SCREEN_WIDTHS_PX`), the round CV button must sit under the floating language toggle, the only CV button shown, and the icon under it, each with its center within 0.5 px of the center of the toggle (`MAX_ICON_OFFSET_PX`, `getBoxCenterDistanceX` of `e2e/utils.ts`), and all three must keep their place once the Experiences page is scrolled to its end. A click on the CV button must download the CV of the language of the page, `CV - Adam Issoufi.pdf` in French and `CV - Adam Issoufi (EN).pdf` in English (`CV_FILE_NAMES`). At 320, 375 and 414 px (`MOBILE_SCREEN_WIDTHS_PX`), the icon must be hidden until the burger opens the menu, then sit under the CV button of the menu, centered the same way.

`e2e/cv-tooltip.e2e.ts` checks the tooltip of the CV buttons, in each language. At the same desktop widths, hovering the floating CV button must show its tooltip whole on the screen (`isBoxInside`, `e2e/utils.ts`), on its left, 8 px away (`tooltip-gap` of the theme, `TOOLTIP_GAP_PX`), with its middle within 0.5 px of the middle of the button (`MAX_TOOLTIP_OFFSET_PX`, `getBoxCenterDistanceY`). The tooltip must stay open while the pointer moves onto it, and close once the pointer leaves. Focusing the button with `Tab` must show it too, and `Escape` hide it. Chrome itself must name the button after its tooltip, hidden or shown, with no description that would repeat it: the test reads the accessibility tree of Chrome through the DevTools protocol (`getBrowserAccessibleText`, `e2e/accessibility.ts`), since Playwright computes names with its own code. At the mobile widths, 800 px high, and on phones held sideways (`LANDSCAPE_PHONE_SCREENS`), where the menu is compact, the CV button of the open menu, focused with `Tab`, must show its tooltip whole above it, at the same gap and centered on it, without covering the last link of the menu, and a first `Escape` must close the tooltip but not the menu.

`e2e/floating-controls.e2e.ts` opens every route of each language at the same widths, and fails when a text, link, button, image or icon of the `<main>` landmark shares some width with the language toggle, the CV button or the GitHub icon (`doBoxesOverlapHorizontally`, `e2e/utils.ts`): the controls are fixed, so such content would pass under them while the page scrolls. Each box is cut to the part that its scrolling or clipping ancestors show, such as a row of cards that scrolls sideways, and what is fixed on the screen is left out. On the Projects page, it checks again once every "Show all" is clicked. The room that `Page` keeps on the right from the tablet breakpoint (`floating-controls-room` in `src/theme/theme.ts`) is what makes it pass.

`e2e/project-cards.e2e.ts` opens the Projects page at 320, 375, 414, 768, 800, 1280, 1440, 1720 and 2400 px (`PROJECT_CARD_SCREEN_WIDTHS_PX`), and checks each section: "Show all" must keep the cards of the row, and only add rows. It measures the cards of the row, clicks "Show all", and fails when a card is wider or narrower than those of the row, or taller or shorter than the same card in the row (by more than 0.5 px, `MAX_CARD_OFFSET_PX`), when a row holds more or fewer cards than the row shows whole (`countWholeCards`: one on a phone, two on a tablet in portrait and up to 913 px, three from 914 px), when a card is not under a card of the first row (`groupCardsIntoRows`), when the columns leave more space on the right of the last one than on the left of the first, so do not fill the section, when a project is missing or when the list or the page scrolls sideways. "Show less" must then bring back the row as it was. A second test goes to the last page of the row with the next page button, which moves the row by the cards it shows whole, and fails when a card of that page is not where the card of the same column is on the first page, with its width: a last page with fewer cards starts on the left. These tests compare the cards of a section with each other, in the same language, so one language is enough. A third one runs in each language: it fails unless the buttons of the section stand from left to right in their tab order (previous, next, "Show all"), the previous arrow is `aria-disabled` and dimmed on the first page, and the next arrow, then the previous one, show every project of the section, the cards shown whole page after page (`filterWholeCards`), up to the bound where the arrow is `aria-disabled`.

`e2e/reduced-motion.e2e.ts` opens every route of each language with the reduced motion preference of the browser (`reducedMotion: 'reduce'`), at 375 and 1440 px (`REDUCED_MOTION_SCREEN_WIDTHS_PX`), and fails when an animation or a transition of the page, a loop or an entrance, lasts longer than 1 ms, its delay included (`INSTANT_ANIMATION_MAX_MS`, `listLastingAnimations` of `e2e/animations.ts`, which describes each one). On the home page, with the pointer over the title, two screenshots taken 1 s apart (`STILLNESS_DELAY_MS`) must be identical: the particle field, the cursor glow and the words of the title stand still. On the Projects page, a card under the pointer must stay flat. At 375 px, the links of the mobile menu must show at once. Two last tests, without the preference, fail unless the home page still moves and a card still tilts, so that these checks cannot pass on a page that never moves.

`e2e/sticky-header.e2e.ts` opens the Experiences page and the Projects page, every "Show all" clicked, in each language, on screens 375, 768, 1024 and 1440 px wide (`STICKY_HEADER_SCREEN_WIDTHS_PX`) and 600 px high (`STICKY_HEADER_SCREEN_HEIGHT_PX`), so that both scroll by more than one screen, and scrolls them to their end. The header must then show whole at the top of the screen, under its blurred band, the `::after` of the header, whose top and height must match those of the header within 0.5 px (`MAX_BAND_OFFSET_PX`), and its logo must still lead to the home page. On short screens, the phones held sideways and 896 × 414 px, which gets the desktop layout (`SHORT_SCREENS`), the header must take at most 15 % of the height (`MAX_HEADER_SCREEN_SHARE`), under a band of its height, with the links and buttons of its row whole in it.

`e2e/mobile-menu.e2e.ts` checks the mobile menu. In each language, on phones held sideways, 568 × 320 and 667 × 375 px (`LANDSCAPE_PHONE_SCREENS`), the open menu must show its links, the CV button and the GitHub icon whole without scrolling, each at least 24 px high, the target size of the Web Content Accessibility Guidelines 2.2 (`MIN_TARGET_SIZE_PX`), and the CV button at least 44 px high (`FINGER_TARGET_HEIGHT_PX`). On a 568 × 240 px screen, lower than the menu (`SHORTER_THAN_MENU_SCREEN`), the menu must scroll to show each of them whole, from its first link, and a wheel scroll over it must move the menu, not the page. On the screens below the tablet breakpoint, phones held upright and sideways and a tablet held upright (`MOBILE_LAYOUT_SCREENS`), a wheel scroll and a swipe over the open menu must leave the page where it was, and once the menu closes the page must still be there and scroll again. On the same screens, the burger must keep its place as the menu opens, and the language toggle must stay usable above the open menu: `Shift+Tab` from the burger must reach it, and a tap on English must take the page to its English URL, the menu still open. The wheel scrolls and swipes go through the DevTools protocol (`scrollDownWithGesture`, `e2e/gestures.ts`), which resolves once the scrolling is done, where `mouse.wheel` of Playwright returns before the page scrolls, so a page that stays still is checked at once.

`e2e/error-pages.e2e.ts` opens the not found page and the unexpected error in each language, on screens of 375 × 667, 1440 × 900 and 2560 × 1440 px (`ERROR_PAGE_SCREENS`). It shows the unexpected error at `/projects` by keeping the chunk of the Projects page from loading (`PROJECTS_CHUNK_PATTERN`), once a reload for a missing chunk counts as just done in session storage, so the page shows its error instead of reloading. A page fails unless its `::before` shows the photo of `StatusPage` (`src/components/StatusPage/constants.ts`), which the server serves, and the center of its message is within 10 % of the height of the page from the center of the page (`MAX_ERROR_MESSAGE_CENTER_OFFSET_RATIO`).

Playwright is a dev dependency, but its browsers are downloaded apart from `node_modules`, to a cache shared by every project of the machine (`~/Library/Caches/ms-playwright` on macOS, `~/.cache/ms-playwright` on Linux): the command above installs only the headless shell of Chromium, which is enough to load, measure and screenshot pages. Each Playwright version needs its own browser build, so run it again after a Playwright update; `pnpm test:browser` says so when the browser is missing.

### Checks

```bash
pnpm typecheck      # Type-check src/, vite/, e2e/, the configs and their specs, then the scripts of scripts/, without building
pnpm lint           # Lint with ESLint
pnpm format:check   # Check that every file follows the Prettier style
pnpm format         # Format every file with Prettier
```

On commit, a husky hook runs ESLint (with `--fix`) and then Prettier on the staged files, and stops the commit on a lint error. `pnpm format` is only needed for files changed outside git.

The CI also lints the GitHub Actions workflows of `.github/workflows/` with [actionlint](https://github.com/rhysd/actionlint): their syntax, their expressions and `if:` conditions, the inputs of the actions they use, and the scripts of their `run:` steps with [ShellCheck](https://www.shellcheck.net/). Neither tool is a dependency of the project. To check a workflow before pushing it, install both (`brew install actionlint shellcheck` on macOS) and run `actionlint` at the root of the repository: without `shellcheck` on the `PATH`, actionlint silently skips the scripts.

## 🌐 Deployment

The site is hosted on [Cloudflare Pages](https://pages.cloudflare.com/), in the `issoufi-fr` project, at [issoufi.fr](https://issoufi.fr/). The CI deploys it with Wrangler once the build and the checks it depends on have passed (formatting, lint, types, tests, bundle size and browser test), so only a tested build goes online:

| Event             | Cloudflare deployment                                                             | GitHub environment |
| ----------------- | --------------------------------------------------------------------------------- | ------------------ |
| Push to `main`    | Production, at [issoufi.fr](https://issoufi.fr/)                                  | `production`       |
| Push to `develop` | Preview, at [develop.issoufi-fr.pages.dev](https://develop.issoufi-fr.pages.dev/) | `preview`          |
| Pull request      | Preview, at `<branch>.issoufi-fr.pages.dev`                                       | `preview`          |

- **Deploy job**: uploads the `dist` artifact of the build job with `cloudflare/wrangler-action`. It needs the `CLOUDFLARE_API_TOKEN` (permission _Account → Cloudflare Pages → Edit_) and `CLOUDFLARE_ACCOUNT_ID` repository secrets, and is skipped with a notice without them. Pull requests from forks and from Dependabot get no secrets, so no preview.
- **Smoke test job**: runs `node scripts/ci/smoke-test.mjs` (the script behind `pnpm smoke-test`) on the new deployment. Its scripts need no dependency, so the job only checks out the repository, sets up Node.js and downloads the `dist` artifact. For production, it also runs the smoke test without a URL, which checks [issoufi.fr](https://issoufi.fr/) itself, and checks that `http://issoufi.fr` and `https://www.issoufi.fr` redirect to `https://issoufi.fr/` (`scripts/ci/check-redirects.mjs`). Both read these addresses from `SITE_URL` and `REDIRECTED_SITE_URLS` in `scripts/ci/constants.mjs`, the one place to change them for the CI scripts. The app writes the same address in its own `SITE_URL` (`src/utils/pages.ts`), and `public/robots.txt` in its `Sitemap:` line: `scripts/ci/utils/pages.spec.js` fails, naming the three files, when one of them changes alone.
- **Manual deployment**: _Actions → CI → Run workflow_ rebuilds and redeploys a branch.
- **Daily production deploy**: every morning at 6:00, Paris time, the workflow `.github/workflows/deploy-production.yml` first releases the version of the day (see Releases), then merges `develop` into `main`, and the push to `main` starts the CI, which tests, builds, deploys and smoke-tests production. So a change merged into `develop` is online the next morning, under a new version, with no pull request to `main`. The workflow:

  1. **Runs once a day**: GitHub schedules run in UTC, so it has two crons, `0 4 * * *` (6:00 in Paris in summer, UTC+2) and `0 5 * * *` (winter, UTC+1). Both run every day, and only the one that matches the current offset of Paris goes on (`scripts/ci/check-deploy-schedule.mjs`), whatever the delay of GitHub's scheduler. The crons are also in `DEPLOY_CRON_BY_UTC_OFFSET_MINUTES` (`scripts/ci/constants.mjs`), and a test fails when the two differ.
  2. **Releases the version of the day** (`release` job, `scripts/ci/merge-release-pr.mjs`): it merges the release pull request once its whole CI passed, publishes the release and waits for the CI of `develop` (see Releases). A day without a release pull request, or whose release cannot be made, leaves a notice, and the deploy goes on with `develop` as it is.
  3. **Fails without the deploy key**, with an error naming the missing `DEPLOY_KEY` secret.
  4. **Stops with a notice when there is nothing to deploy**: `main` holds merge commits that `develop` lacks but no content of its own, so the same tree on both branches means that production already serves `develop`.
  5. **Only deploys a tested commit**: it stops with a notice unless the last run of `ci.yml` on `develop` for that exact commit succeeded, whether a push started it or the daily release (`scripts/ci/check-develop-ci.mjs`), for example while that run is still going or after it failed. The next morning, or a manual run, deploys it once the CI passes.
  6. **Promotes it**: it checks out `main` with the deploy key, merges the tested commit (even when `develop` moved since) with a merge commit, `chore: deploy develop to production`, and fails unless the result has exactly the tree of that commit, which happens when `main` holds a change that `develop` lacks: merge `main` into `develop` first. It then pushes to `main`. A push made with the `GITHUB_TOKEN` would start no workflow, while one made with a deploy key does, so the CI deploys production.
  7. **Reports** in its job summary the commits deployed, one per pull request merged into `develop` (first parents only), and links the CI run of `main` (`scripts/ci/write-deploy-report.mjs`).

  Runs never overlap (`concurrency`), and the `GITHUB_TOKEN` of the workflow only reads (`contents: read`, `actions: read`), except in the `release` job, which merges the release pull request and starts workflows (`contents`, `pull-requests` and `actions: write`). _Actions → Deploy to production → Run workflow_ releases and deploys at once; with **dry_run** checked, it runs the CI of the release pull request without merging it, runs every check and the merge into `main`, connects with the deploy key (`git push --dry-run`), and says in its summary what would be deployed, without pushing. Being scheduled, the workflow only runs from the default branch, `develop`, and GitHub disables it after 60 days without activity on the repository: re-enable it from the Actions tab then.

  **Setup**, done by the site owner in the repository settings, never by the workflow or an agent:

  - **Deploy key**: _Daily production deploy_ (_Settings → Deploy keys_), **with write access**. Its private key is the `DEPLOY_KEY` repository secret (_Settings → Secrets and variables → Actions_). To replace it, create a key pair (`ssh-keygen -t ed25519 -f deploy_key -N ''`), add the public key as a deploy key with write access, store the private key in `DEPLOY_KEY`, then delete the old key and both local files.
  - **Rulesets** (_Settings → Rules → Rulesets_), one per branch, each refusing deletions and force pushes and requiring a pull request whose status checks pass:
    - _Protect main (daily deploy from develop)_, on `main` alone, with _Deploy keys_ as bypass actors (always), so that the push of the workflow goes through without a pull request;
    - _Protect develop_, on `develop` alone, with no bypass.

  On a personal repository, GitHub refuses the GitHub Actions app as a bypass actor, which is why the push uses a deploy key.

Every other file keeps the default policy of Cloudflare Pages, which has browsers revalidate it, since its URL stays the same when its content changes: the HTML pages, `robots.txt`, `sitemap.xml` and the files of `public/`, the fonts of `public/fonts/` included, whose names other scripts read. `vite.config.spec.ts` checks that the build writes it and that every file of `assets/` has a hash in its name, and `vite.standalone.config.spec.ts` that the standalone build leaves it out.

When the browser blocks the storage, the root opens in French. The path helpers (`localizePath`, `getPathLanguage`…) are in `src/i18n/utils.ts`.
- **Project likes**: the heart of each project card is the visitor's own like, with no count: no project is liked on a first visit, and the site shows no like that the visitor did not give. The button stores the ids of the liked projects in `localStorage` (`likedProjects` key, a JSON list such as `[1,5]`, `src/pages/Projects/Project/storage.ts`), read again on each visit, so a like survives a reload and a change of language; when the browser blocks the storage, the button still toggles, for the visit only (`useLikes`, `src/pages/Projects/Project/hooks`). The `id` of each project of `src/pages/Projects/.data/*.json` keys its like: it is an integer that no other project of either file has, which `Projects.spec.jsx` checks, and it stays with its project, or the likes already given would move to another one. A count shared between visitors would need a server, such as a Cloudflare Pages Function with a KV namespace or a D1 database.

The project cards keep only keys in their data: each project of `src/pages/Projects/.data/*.json` names its texts with a `nameKey` and a `typeKey`, translated under `projects.names` and `projects.types` (`translateProjects`, `src/pages/Projects/utils.ts`), and `Projects.spec.jsx` fails when a language lacks one. - **Not found pages**: the plugin also emits a not found page per language, `404.html` and `en/404.html`, with the "page not found" title in its language and a `noindex` tag. Cloudflare Pages serves, with a real `404` status, the `404.html` of the closest folder up a path that matches no file: `en/404.html` under `/en/`, `404.html` anywhere else. The URL is kept, with no redirect, and the app shows its NotFound page, in the language of the URL. Because `404.html` exists, Cloudflare's single-page-app fallback is off, which is why every route needs its own HTML file.
- **Code splitting**: the home page is in the main chunk, and every other page (`Projects`, `Experiences`, `NotFound`) is loaded with `React.lazy` on its first visit, from its own chunk named after its folder (`vite.config.ts`). The header stays on screen while a page loads. The burger icon loads the light build of `lottie-web` (SVG only) after the first render, so the animation never delays a page. Each deployment replaces the chunks of the previous one: a page opened before a deployment reloads once when it cannot load a chunk any more (`useReloadOnStaleChunk`, `src/App/hooks`), at most once a minute so a missing chunk never causes a loop. Meanwhile, the page it was loading stays blank below the header instead of failing (`keepPendingWhileReloading`, `src/App/utils.ts`). Import a lazily loaded page from its folder only, never through a shared barrel, which would put it back in the main chunk.
- **Preloading the page chunk**: each generated page, `404.html` included, has a `modulepreload` link to the chunk of the page it shows, the chunk built from the `index.ts` of its `folder` (`getPageChunkFile`, `vite/utils.ts`). On a direct visit, the browser downloads it at the same time as the main chunk, instead of once the main chunk has run. The home page is in the main chunk and gets none. `vite.config.spec.ts` checks that each page preloads its own chunk and no other.

The header stays usable, and going to another page renders the routes again. React logs the error to the console; nothing is reported anywhere else.

The test job measures the coverage, adds its total to the job summary and keeps the HTML report as the `coverage` artifact for 14 days. The scripts behind these summaries live in `scripts/ci/`. ## 🏷 Releases

[`CHANGELOG.md`](CHANGELOG.md) is written by [release-please](https://github.com/googleapis/release-please) from the Conventional Commits, never by hand:

1. Each push to `develop` updates a release pull request against `develop` (_chore: release x.y.z_), with the next version in `package.json` and the new `CHANGELOG.md` entry. The workflow `.github/workflows/release.yml` maintains it. When `develop` holds no change to release since the last version, there is no release pull request.
2. Every morning, before the production deploy, the `release` job of `.github/workflows/deploy-production.yml` releases it, with no one involved (`scripts/ci/merge-release-pr.mjs`):

   1. it finds the open release pull request, by its `autorelease: pending` label and its `release-please--branches--develop--` branch, and stops with a notice when there is none;
   2. it runs `ci.yml` on its branch, as _Run workflow_ does, and waits for the run, up to 20 minutes (`RUN_WAIT_ATTEMPTS` and `RUN_WAIT_DELAY_MS`, `scripts/ci/constants.mjs`). It stops with a notice unless the whole run passed, its preview deployment and smoke test included;
   3. it merges the pull request with a merge commit, at the commit that the CI tested: GitHub refuses the merge when release-please moved the branch since, or when a required check is missing or failed. The `commits` and `dependencies` checks only run for a pull request event, so they are skipped in that run, which GitHub counts as passed: the release pull request, written by release-please, gets no commitlint or dependency review;
   4. it starts `release.yml` and `ci.yml` on `develop`, and waits for the CI, so that the deploy finds the new commit of `develop` tested.

   It never fails the deploy: a release that cannot be made leaves a notice, or a warning when something unexpected happened, and the next morning tries again. GitHub Actions opens the release pull request, and GitHub holds the workflows of such a pull request until a person with write access approves them (_Approve workflows to run_). Can the `GITHUB_TOKEN` approve the runs of its own pull request? No, as far as GitHub documents it: [Triggering a workflow](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow) leaves the approval to a person with write access, and recommends a GitHub App installation token or a personal access token to avoid it, while the REST endpoint that approves a run is documented for pull requests from forks only. So the job does not rely on it. Besides, a merge made with the `GITHUB_TOKEN` starts no push workflow. The job starts each workflow by hand instead (`workflow_dispatch`), which GitHub runs at once even when the `GITHUB_TOKEN` asks, and the deploy accepts a run of `ci.yml` on `develop` started by hand. So the daily release needs no secret.

3. Merging it tags the version (`vX.Y.Z`) and publishes a GitHub release, when `release.yml` runs on `develop`. GitHub attaches the source code to it (zip and tar.gz), and the `standalone-build` job of the same workflow attaches `issoufi.fr-vX.Y.Z.zip`, the standalone build below.
4. The production deploy that follows (see Deployment) puts the release in production with the rest of `develop`, and the header shows its version.

The release pull request can still be merged by hand: approve its workflows on the pull request, since its checks are required to merge it.

The version follows the commits: `fix` bumps the patch version, `feat` the minor version, and a breaking change (`feat!:` or a `BREAKING CHANGE:` footer) the major version. The changelog lists features, fixes, performance improvements, reverts, refactors and documentation; `build`, `ci`, `test`, `style` and `chore` commits stay out of it (`release-please-config.json`). It starts with the React 19 and Vite rewrite of March 2026.

### Standalone build

`issoufi.fr-vX.Y.Z.zip` holds one folder, `issoufi.fr-vX.Y.Z/`, with the site as it was at that version: a visitor unzips it and opens `index.html` with a double click, with no server, no Node.js and nothing to install, every page and the language toggle included. Its `README.txt` (`vite/standalone/README.txt`) says so in French and in English. The site requests nothing from the network: its fonts are embedded in `index.html`, so it renders the same offline.

The production build cannot open from the disk: its URLs are absolute (`/assets/…`), which point to the root of the disk under `file://`, `BrowserRouter` would read the path of the file as the route and show the not found page everywhere, and browsers refuse to load module scripts, such as the chunks of the lazily loaded pages, from `file://`. `pnpm build:standalone` therefore builds it again with `vite.standalone.config.ts`, which takes the config of `vite.config.ts` as it is, with a relative base (`base: './'`) and the dynamic imports inlined (`inlineDynamicImports`), so the whole app, the pages loaded lazily and `lottie-web` included, is one script. Four plugins do the rest:

- `standalone-hash-router` resolves the imports of `react-router` from `src/` to `vite/standalone/react-router.ts`, whose `BrowserRouter` is the `HashRouter`, so the routes read the hash of the URL (`index.html#/projects`);
- `standalone-relative-public-urls` turns the URLs of the files of `public/` that the code writes as strings (`'/home.webp'`, the `imageUrl` of the projects, the CV) into URLs relative to the page (`'./home.webp'`), since Vite copies these files next to `index.html`. Write such a URL as one whole string, never built from parts (`'/' + name`), or the standalone build will not find the file;
- `standalone-embedded-fonts` writes the content of each font file of `FONT_FACES` (`src/theme/constants.ts`) as a data URL in place of its URL in the `@font-face` rules of `index.html` (`toFontDataUrls`), so the page holds its fonts and renders in them offline in any browser, and removes the links that preload them (`removeFontPreloads`). The build fails when one of these files is missing from `public/fonts/`;
- `standalone-page` removes the other pages (`projects.html`, `experiences.html`, `404.html`) and `_headers`, which only a web server needs, puts the code of that script in the `<script type="module">` tag of `index.html` (`inlineScript`), so the page loads no script from a file, and adds the `README.txt`. Before inlining it, it replaces with `void 0` the `__VITE_PRELOAD__` markers that Vite leaves next to the inlined dynamic imports (`removePreloadMarkers`), which would make each lazy page throw. This takes a few lines, where `vite-plugin-singlefile` would pull in `micromatch` and `braces`, which has a high severity advisory with no fixed version (GHSA-vfj7-8cjw-p6xm).

The production build and its deployment do not change: neither `vite.config.ts` nor the code of the app knows about the standalone build. `vite.standalone.config.spec.ts` builds it in memory and checks that `index.html` is its only page and loads no script from a file, that `_headers` is left out, with no preload marker left, that the app imports the hash router, that no URL of a file of `public/` is absolute, that the fonts are embedded and not preloaded, that no host of Google is named and that the `README.txt` is there; the helpers are in `vite/standalone/utils/`, one file per topic (`bundle.ts`, `fonts.ts`, `public-files.ts`, `router.ts`, `strings.ts`), each with its spec. To try it, run `pnpm build:standalone` and open `dist-standalone/index.html` in a browser.

The job runs only when release-please has just created a release (its `release_created` output), checks out the tagged commit, runs `pnpm build:standalone`, zips `dist-standalone/` under the name of the archive and uploads it with `gh release upload` (`--clobber`, so running the job again replaces it). The release workflow needs no other secret than its own token, which may write the contents of the repository.

## 📝 Conventions

- **Branches**: `main` is production and `develop`, the default branch, the integration branch. A ruleset protects each of them (_Protect main (daily deploy from develop)_ and _Protect develop_): changes go through a pull request whose CI checks pass, and force pushes and deletions are refused. The one exception is the daily production deploy: every morning, its deploy key pushes the merge of `develop` into `main`, which the ruleset of `main` lets through (see Deployment). The `production` environment only accepts deployments from `main`. Each ticket is worked on in its own [Worktrunk](https://worktrunk.dev) worktree next to the repository (`AIssoufi.github.io.ISF-35`), on a branch named after its reference: the `ISF-` autolink turns `ISF-35` into a link to issue #35. The branch starts from `develop` (`wt switch --create ISF-35 --base develop`) and goes back into it through a pull request that says `Closes #35`, once the CI passes. `.config/wt.toml` installs the dependencies of each new worktree and writes its port to `.env.local` (see Development). No pull request targets `main`: `develop` reaches it every morning once its CI passed.
- **Commits**: [Conventional Commits](https://www.conventionalcommits.org/) enforced via commitlint. They also set the next version and the changelog (see Releases).
- **Linting**: ESLint (`eslint.config.js`) with the recommended rules of ESLint and typescript-eslint, React Hooks (including the React Compiler rules) and React Refresh. It also forbids importing `styled-components` directly, importing the style file of a component (`Name.styled`) from outside its folder, and rendering a `ul` other than through `List`.
- **Formatting**: Prettier (via lint-staged + husky)
- **Language**: code, comments and docs are in English. Only user-facing texts are translated.
- **Styles**: styled-components read every color, spacing, size, font, radius, shadow, duration, easing and breakpoint from the design tokens of `src/theme` with the [xstyled](https://xstyled.dev/) `th` helpers (`th.color('accent')`, `th.space(16)`, `th.size(36)`, `th.radius('md')`…), and keyframes from the `theme` object. No hard-coded values: `src/theme/theme.spec.jsx` fails on a length in pixels, a duration, a color or an easing written by hand in a style file, and allows only zero, percentages, viewport units, angles and unitless numbers. The semantic tokens of `theme.ts` only read the primitive scales of `tokens.ts`, or build alpha variants from them, and the same spec fails on a value written by hand there. Every styled-components API is imported from `@xstyled/styled-components`.
- **Fonts**: the site serves its two fonts itself, from `public/fonts/`, and requests nothing from Google: Montserrat, a variable font that draws every weight from 100 to 900, for the texts, and Saira Stencil One for the logo. They are the `latin` subsets that Google Fonts served, byte for byte, as `woff2` files: ASCII, Latin-1 with the French accents, `œ` and the punctuation of U+2000–206F (`LATIN_UNICODE_RANGE`); a character outside them, such as `→`, shows in the next font of the stack, as it did before. Google Fonts served Windows and Linux files with hinting, and macOS, iOS and Android lighter ones without: the site serves the hinted ones, which the others ignore, so every system draws the text as before. Their license, the SIL Open Font License, is served next to them (`montserrat-OFL.txt`, `saira-stencil-one-OFL.txt`). `FONT_FACES` (`src/theme/constants.ts`) lists them once, and the `font-faces` plugin of `vite.config.ts` adds to the head of every page a link that preloads each file, since every page shows both fonts, then a `<style>` of their `@font-face` rules, written by `renderFontFaces` (`src/theme/utils.ts`) with `font-display: swap` (`getFontFaceTags`, `vite/utils.ts`). The rules stay out of the styles of styled-components: Chrome loads the fonts again each time a component adds a rule to that style sheet, and shows the fallback font meanwhile. A script that renders a page in these fonts, such as `pnpm og-image`, calls `renderFontFaces` with a `getUrl` that reads each file as a data URL, and the standalone build embeds them the same way: keep the names and the folder of the files, which these scripts read. Their URL therefore does not change with their content, so they keep the default cache of Cloudflare Pages rather than the year of `assets/` (see Cache headers). The CV does not use them: a variable font would become Type 3 fonts in its PDF, so it prints in static files of its own (see CV). A new font needs its file and its license in `public/fonts/`, and its entry in `FONT_FACES`: `src/theme/constants.spec.ts` checks the files and the licenses, and `vite.config.spec.ts` that every page preloads and declares each font.
- **Components**: one folder per component (`Name.tsx`, `Name.spec.jsx`, `Name.styled.ts`, `index.ts`), styles imported only by their own component, optional props that tolerate missing values, and JSDoc on every component and prop. See [`CLAUDE.md`](CLAUDE.md) for the details.
- **Accessibility**: every page renders a single `<main>` landmark, its `Page` component, and a single `h1`, visually hidden when the design shows none; its sections use `h2` and below. The test of each page checks both. Every list is a `List` (`src/components/List`): the global style removes the bullets of lists, and Safari then stops exposing a `ul` as a list, which `role="list"` restores, so VoiceOver still announces it and counts its items. The site respects the reduced motion setting of the system (`prefers-reduced-motion: reduce`, `REDUCED_MOTION_QUERY` in `src/theme/constants.ts`), which people with vestibular disorders turn on: `GlobalStyle` then plays every CSS animation once and makes it and every transition instant (the `instant` duration, important so that it also wins over the inline styles of the hooks), so nothing loops and what slides in shows at once, and the effects written in JavaScript read `usePrefersReducedMotion` (`src/hooks`) to stand still: the particle field draws one still frame, the cursor glow is hidden, the parallax, the magnetic buttons and the words of the title no longer follow the pointer, and the project cards no longer tilt toward it (`useCardTilt`), only their light does. A new effect that follows the pointer or loops in JavaScript must do the same.
