# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
pnpm dev          # Start dev server on port 3000, or on PORT (.env.local in a worktree)
pnpm build        # Type-check + production build (tsc && vite build)
pnpm size         # After a build: fails over the gzip budgets of scripts/ci/constants.mjs (home page first load, all chunks)
pnpm smoke-test <url> # After a build: checks that a deployed site serves the pages of dist/
pnpm og-image     # Regenerates public/og-image.jpg in Chromium (Playwright); needs the network
pnpm preview      # Preview production build on port 4173, or on PORT
pnpm typecheck    # Type-check only: src/, vite/, e2e/, the configs and vite.config.spec.ts, then scripts/ (scripts/tsconfig.json)
pnpm lint         # ESLint (eslint.config.js)
pnpm test         # Run tests once
pnpm test:watch   # Run tests in watch mode
pnpm test:coverage # Run tests with coverage; fails below COVERAGE_THRESHOLDS_PERCENT (vite.config.ts)
pnpm test:browser  # After a build: Playwright checks in Chromium that no page scrolls sideways, that the timeline dots sit on its line, that the GitHub icon sits centered under the language toggle and the CV button and that the project cards keep their size and their columns, in "Show all" and on the last page of the row
pnpm format:check # Check Prettier formatting, as the CI does
pnpm format       # Format every file with Prettier
```

ESLint uses the recommended rules of ESLint, typescript-eslint, React Hooks (with the React Compiler rules) and React Refresh. Formatting is handled automatically by Prettier via lint-staged on commit.

## Architecture

Personal portfolio SPA built with React 19 + TypeScript + Vite.

**Entry point**: `src/index.tsx` mounts to the `#welcome` DOM element.

**Routing** (`src/App/App.tsx`): flat BrowserRouter setup with three routes — `/` (Home), `/projects`, `/experiences` — and a `*` catch-all rendering the NotFound page at the requested URL, without redirecting. Home is in the main chunk; the other pages are loaded with `React.lazy` on their first visit, each from its own chunk, so import them from their own folder (`../pages/Projects`), never through a barrel that would put them back in the main chunk. A Forbidden page (403) exists for content the visitor may not access. The routes sit in `RouteErrorBoundary` (`src/App`), below the header: a page that throws or whose chunk fails to load shows a translated error with a reload button, and the next navigation renders the routes again. After a navigation by link, `PageHeadingFocus` (`src/App`), inside the `Suspense` of the routes, gives the keyboard focus to the first `h1` of the new page, so every page needs one. Each route also needs an entry in `PAGES` (`src/utils/pages.ts`), which drives its metadata and the HTML file generated for it at build time. This is required: the build also emits a `404.html`, which turns off Cloudflare's single-page-app fallback, so a route without its own HTML file would return a 404 on reload. The `folder` of the entry names the page folder whose chunk that HTML file preloads (`modulepreload`), so a direct visit downloads it with the main chunk. The header shows the version of the build after the logo, `__APP_VERSION__`, which `vite.config.ts` reads from `package.json` (`define`, typed in `src/vite-env.d.ts`), and the official GitHub icon (`GitHubLink`, `src/App/Header`), centered under the floating language toggle from the tablet breakpoint, and under the CV button in the mobile menu.

**Component conventions**: every component lives in its own folder named after it:

- `ComponentName.tsx` — the component, with JSDoc on the component and on every prop
- `ComponentName.spec.jsx` — its tests, **required** for every component, at least a render without props
- `ComponentName.styled.ts` — styled-components styles, when it has any (not documented with JSDoc)
- `index.ts` — re-export

Sub-components get the same structure in their own folder inside their parent's folder. A component shared by several sub-components of a parent sits at the root of that parent's folder. Components shared across pages live in `src/components/` (e.g. `StatusMessage`, or `Page`, the `<main>` landmark that every page extends with `styled(Page)` and a `backgroundImage` prop). A page has exactly one `<main>`, its `Page`, so nothing inside it renders another, and exactly one `h1`, visually hidden when the design shows none (as on `/projects`), with `h2` and below for its sections; each page spec checks both. Every list is a `List` (`src/components/List`), extended with `styled(List)`: a `ul` with `role="list"`, since the global style removes the bullets and Safari then stops exposing a `ul` as a list (ESLint `no-restricted-syntax` refuses `styled.ul` and `<ul>` in the other TypeScript files of `src`), and the spec of each list checks its role. A `ComponentName.styled.ts` is imported only by its own component (ESLint `no-restricted-imports` enforces it): styles shared by several sub-components go in a lowercase style module at the root of their parent (e.g. `src/pages/Experiences/timeline.styled.ts`), and styles shared by pages go in a component of `src/components/`. Props are optional by default, and components must render without crashing when a prop is missing.

**Styling and design tokens**: `src/theme/tokens.ts` holds the primitive scales (palette, spacing, sizes, font sizes…) and `src/theme/theme.ts` the semantic tokens, following the xstyled theme conventions (`colors` with `-aNN` alpha variants, `space`, `sizes`, `fontSizes`, `radii`, `shadows`, `zIndices`, `durations`, `timingFunctions`, `screens`…). Import `styled`, `css`, `keyframes`, `createGlobalStyle`, `ThemeProvider` and `th` from `@xstyled/styled-components` only, never from `styled-components` directly (ESLint and a test enforce it). Styled-components read the tokens with the `th` helpers (`th.color('accent-a55')`, `th.space(16)`, `th.radius('md')`, `th('screens.tablet')`); color names are type-checked, and `src/theme/theme.spec.jsx` checks that every token used in a style file exists. A negative space token is written `th.space(-8)`. `keyframes` have no theme context, so they read the `theme` object (`translateY(-${theme.space[12]})`), as JavaScript code (canvas, inline styles) does. A value shared with JavaScript stays a named constant, interpolated with its unit (`${BUTTON_WIDTH_PX}px`). `App` provides the `ThemeProvider` and `GlobalStyle` (which replaced `index.css`). Never write a raw color, spacing, size, font size, radius, shadow, duration, easing, z-index or breakpoint in a style file: look for an existing token first, then add one to the right scale. `theme.spec.jsx` fails on any length in `px`, `em`, `rem` or `ch`, duration, color, easing, or raw z-index, font weight or line height written in a `*.styled.ts` file or `GlobalStyle.ts` (`findRawValues`, `src/theme/testUtils.js`); zero, percentages, viewport units, angles and unitless numbers (scale factors, opacities, flex factors) may stay raw. `theme.ts` writes no value itself: each semantic token reads a primitive of `tokens.ts` (`radii[12]`, `easings.easeOutBack`, `shadowShapes['4-24']`), or a color built from one with `alphaVariants`, and `theme.spec.jsx` fails on a literal or a raw value written there (`findRawThemeValues`, same file). A new value therefore goes into a primitive scale first.

**Logic, constants and hooks**: magic numbers are named constants with their unit (`constants.ts` next to their users), computations are pure helpers in `utils.ts` with tests, and stateful effects are hooks in `hooks/useThing/` with tests (see `src/pages/Home/hooks`).

**Static data**: page-level data lives in `.data/*.json` files inside the page directory (e.g. `src/pages/Projects/.data/freelance-projects.json`).

**Link preview image**: `public/og-image.jpg` is generated by `pnpm og-image` (`scripts/og-image/`) from the French texts, the theme, the background photo and the particle field of the home page, read through Vite. It runs on demand: regenerate it and commit it when one of them changes.

**Assets**:

- Background images are served from `public/` and referenced with absolute paths (e.g. `'/projects.webp'`)
- SVGs are imported as React components via `vite-plugin-svgr`
- Lottie animations use JSON files co-located with the component

**Tests**: Vitest + Testing Library. Test files are co-located with the code they test: `*.spec.jsx` for components, `*.spec.ts` for helpers and hooks, `*.spec.js` for the script helpers of `scripts/ci/utils/` and `scripts/og-image/utils/` and for the JavaScript test helpers (`src/styleTestUtils.js`, `src/pages/testUtils.js`, `src/App/testUtils.js`, `src/theme/testUtils.js`). `vite.config.spec.ts` builds the site in memory with the real config and checks the generated pages, such as the chunk each one preloads. The setup file, `src/setupTests.ts`, extends Vitest with `@testing-library/jest-dom` and wraps every `render` of Testing Library in the theme and global styles of the app (`withTheme`, `src/testUtils.tsx`), around the wrapper a spec passes, so a spec adds no `ThemeProvider` (only the specs of `src/theme` render it, to test the theme and the global styles themselves). It also gives no canvas context, and fails a test that logs with `console.error`: fix the warning (an update outside `act`, such as the burger icon drawn once lottie-web is loaded, is awaited with `waitFor`, here `waitForBurgerIcon` of `src/App/testUtils.js`), or silence an expected error with `vi.spyOn(console, 'error').mockImplementation(() => {})`. As in production, styled-components inserts each rule into the CSSOM with `insertRule` (`SC_DISABLE_SPEEDY: 'false'` in the `test.env` of `vite.config.ts`), since jsdom parses a whole `<style>` again on every change of its text, which made the suite several times slower: the `<style>` elements hold no text, so read the rules through `document.styleSheets`, with `listStyleRules` and `declaredStyle` of `src/styleTestUtils.js`, shared by the specs of every folder. `src/setupTests.ts` also fails a test whose component inserts a rule that the CSSOM refuses or that holds the source of a function (a function interpolated outside a `css` block), since browsers drop it (`logDroppedCssRules`, `src/cssRuleGuard.ts`). The CSSOM serializes a declared value as browsers do (a length of `0` as `0px`, `calc(24px - 5px)` as `calc(19px)`, `url("/a.webp")` with quotes): build an expected value from tokens with `serializeCssValue`. jsdom ignores media queries (except `all` and `screen`), does not focus an element hidden by `display: none`, converts computed lengths into pixels, and leaves out of `getComputedStyle` a rule whose selector list holds a pseudo-element (`*, *::before, *::after`): read the declared rules in those cases. `src/setupTests.ts` runs for every spec, including the node ones: guard any DOM global it touches. When an AI agent runs Vitest, it hides the console output of the passing tests: add `--reporter=default` to see it. Components that need routing must be wrapped with `<BrowserRouter>` in tests. The helpers shared by the page tests live in `src/pages/testUtils.js`, in JavaScript like the specs, such as `isPublicFile`, which checks that an image URL names a file of `public/`.

**Browser tests**: jsdom computes no layout, so what needs one is checked in Chromium by the Playwright tests of `e2e/` (`*.e2e.ts`, `playwright.config.ts`), on the production build that `pnpm preview` serves on the port of the worktree. In each language of `LANGUAGES` (stored in `localStorage`), at 320, 375, 414 and 1440 px, `horizontal-overflow.e2e.ts` opens every route of `PAGES` and an unknown path, and fails when a page is wider than the screen; `timeline.e2e.ts` opens the Experiences page, and fails when the center of a dot of its timeline is more than 0.5 px from the center of the line; `github-link.e2e.ts` fails when the GitHub icon is not centered under the language toggle at 800, 1440 and 1920 px, or moves when the page scrolls, and when the mobile menu does not show it centered under the CV button at 320, 375 and 414 px. The line and the dots are pseudo-elements, which the DOM gives no box for: the timeline test measures them through the DevTools protocol (`e2e/pseudo-elements.ts`), and finds them by the `data-timeline-line` and `data-timeline-dot` attributes, whose value names the pseudo-element that draws them (`before` or `after`), so keep each attribute in step with its CSS. At 375, 800, 1280, 1440, 1720 and 2400 px, `project-cards.e2e.ts` clicks "Show all" in each section of the Projects page, and fails unless the cards keep the width and height of the row, with as many per row as the row shows whole, every row starting on the left, and nothing scrolling sideways, and unless the last page of the row puts its cards in the columns of the first page. Install the browser once with `pnpm exec playwright install --only-shell chromium`. Their helpers are tested by Vitest like any other (`e2e/utils.spec.ts`, `e2e/pseudo-elements.spec.ts`).

**CI and deployment**: `.github/workflows/ci.yml` checks formatting, lint, types (`src/`, `vite/`, `e2e/`, the configs and `scripts/`), tests with coverage thresholds and the bundle size, builds, checks in Chromium that no page of the build scrolls sideways, that the timeline dots sit on its line, that the GitHub icon sits centered under the language toggle and the CV button and that the project cards keep their size and their columns, in "Show all" and on the last page of the row (browser-test job, Chromium cached per Playwright version), then deploys the `dist` artifact to Cloudflare Pages (project `issoufi-fr`) with Wrangler and smoke-tests it: `main` goes to production at issoufi.fr, any other branch to a preview. On pull requests, it also checks the commit messages with commitlint (except Dependabot's) and runs GitHub's dependency review. Cloudflare's own automatic builds are paused. `.github/workflows/deploy-production.yml` puts `develop` in production every morning at 6:00, Paris time: of its two crons (`0 4 * * *` in summer, `0 5 * * *` in winter, kept equal to `DEPLOY_CRON_BY_UTC_OFFSET_MINUTES` of `scripts/ci/constants.mjs` by a test), only the one of the day's offset goes on (`check-deploy-schedule.mjs`). It stops with a notice when the trees of `main` and `develop` are the same, or unless the last push run of `ci.yml` on `develop` for that exact commit succeeded (`check-develop-ci.mjs`), and fails when the `DEPLOY_KEY` secret is missing. Otherwise it merges that commit into `main` with a merge commit (`chore: deploy develop to production`), fails unless the result has the tree of the tested commit, and pushes it with the deploy key: unlike the `GITHUB_TOKEN`, that push starts the CI on `main`, which deploys production. A `workflow_dispatch` runs it at once, and its `dry_run` input merges without pushing (`git push --dry-run`); its job summary lists the commits deployed (`write-deploy-report.mjs`). Being scheduled, it only runs from the default branch, `develop`. `.github/workflows/rebuild.yml` reruns the CI on `main` on the first day of every month, so the years of experience written in the HTML files stay right, and `release.yml` maintains the release-please pull request. The helpers of the CI scripts are in `scripts/ci/utils/`, one file per topic (`bundle.mjs`, `bundle-report.mjs`, `coverage.mjs`, `deploy-report.mjs`, `html.mjs`, `pages.mjs`, `job-summary.mjs`, `lists.mjs`, `numbers.mjs`, `schedule.mjs`, `step-output.mjs`, `workflow-runs.mjs`), each with its tests.

## Conventions

- **Branches**: `main` is production, `develop` the integration and default branch. Two rulesets, _Protect develop_ (25318593, no bypass) and _Protect main (daily deploy from develop)_ (25335502), refuse direct pushes, force pushes and deletions: every change goes through a pull request with passing checks. The one exception is `main`, updated every morning by `deploy-production.yml`, which pushes its merge of `develop` with the read-write deploy key _Daily production deploy_ (private key in the `DEPLOY_KEY` secret), the only bypass actor of the ruleset of `main`. The site owner manages the key, the secret and the rulesets: never change them. Work on each ticket in its own Worktrunk worktree, on a branch named after the ticket reference (`ISF-35`, from the `ISF-` autolink to the issues). Start it with the `ticket-worktree` skill (`ticket.mjs start ISF-35`), which fetches `develop` and branches from `origin/develop`, rather than with a bare `wt switch --create`. Open its pull request against `develop` with `Closes #35`. No pull request targets `main`, not even for a release: `develop` reaches it every morning once its CI passed, so a change merged into `develop` is in production the next day.
- **Ports**: when a worktree is created, `.config/wt.toml` writes `PORT=<port>` to its `.env.local`, a port derived from the branch (10000–19999). `vite.config.ts` reads it with `getServerPorts` (`vite/utils.ts`) for both `pnpm dev` and `pnpm preview`, and `playwright.config.ts` for the preview server of `pnpm test:browser`, so read a worktree's port in its `.env.local` rather than assuming 3000. Without `PORT`, as in the main checkout, they use 3000 and 4173. A taken port stops the server with an error (`strictPort`) instead of moving it to another port, and `BROWSER=none` stops Vite from opening the browser.
- **Commits**: Conventional Commits enforced via commitlint + husky (`feat:`, `fix:`, `refactor:`, etc.). They set the next version and `CHANGELOG.md`, which release-please writes: never edit the changelog by hand, and use `feat`/`fix` only for changes a visitor of the site would notice, since those appear in it.
- **Formatting and linting**: on commit, lint-staged runs `eslint --fix` then Prettier on staged files, one after the other (`--concurrent false`, as both write the same files). A lint error stops the commit.
