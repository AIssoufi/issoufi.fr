# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
pnpm dev          # Start dev server on port 3000, or on PORT (.env.local in a worktree)
pnpm build        # Type-check + production build (tsc && vite build)
pnpm build:standalone # Type-check + the standalone build in dist-standalone/: the site in one index.html that opens from the disk, attached to each GitHub release
pnpm size         # After a build: fails over the gzip budgets of scripts/ci/constants.mjs (home page first load, all chunks)
pnpm smoke-test [url] # After a build: checks that a deployed site, production (SITE_URL of scripts/ci/constants.mjs) without a URL, serves the pages of dist/, its robots.txt and its sitemap.xml
pnpm og-image     # Regenerates public/og-image.jpg and public/og-image-en.jpg in Chromium (Playwright), in the fonts of public/fonts/
pnpm preview      # Preview production build on port 4173, or on PORT
pnpm typecheck    # Type-check only: src/, vite/, e2e/, the configs and their specs, then scripts/ (scripts/tsconfig.json)
pnpm lint         # ESLint (eslint.config.js)
pnpm test         # Run tests once
pnpm test:watch   # Run tests in watch mode
pnpm test:coverage # Run tests with coverage; fails below COVERAGE_THRESHOLDS_PERCENT (vite.config.ts)
pnpm test:browser  # After a build: Playwright checks in Chromium that no page scrolls sideways or requests Google, that the timeline dots sit on its line, that each page is served at its URL in each language (`/en/…`), that the CV button and the GitHub icon sit centered under the language toggle, the icon under the CV button of the mobile menu, and that no content passes under them, that the tooltip of the CV button shows whole next to it, and that the project cards keep their size and their columns, in "Show all" and on the last page of the row
pnpm format:check # Check Prettier formatting, as the CI does
pnpm format       # Format every file with Prettier
```

ESLint uses the recommended rules of ESLint, typescript-eslint, React Hooks (with the React Compiler rules) and React Refresh. Formatting is handled automatically by Prettier via lint-staged on commit.

## Architecture

Personal portfolio SPA built with React 19 + TypeScript + Vite.

**Entry point**: `src/index.tsx` mounts to the `#welcome` DOM element.

**Routing** (`src/App/App.tsx`): BrowserRouter setup with three routes per language — `/` (Home), `/projects`, `/experiences` — and a `*` catch-all rendering the NotFound page at the requested URL, without redirecting. The URL names the language: French, `DEFAULT_LANGUAGE`, has no prefix, and every other language of `LANGUAGES` has the same routes behind its prefix (`/en/`, `/en/projects`). `UrlLanguage` (`src/App`) switches i18next to the language of the URL after each navigation, `useUrlLanguage` (`src/hooks`) reads it, and the path helpers (`localizePath`, `getPathLanguage`, `removeLanguagePrefix`) are in `src/i18n/utils.ts`. Every internal link is a `LocalizedLink` (`src/components`), whose `to` is the path in the default language, or a path built with `localizePath`, so a visitor stays in the language they browse in. The language toggle goes to the same page in the other language and stores the choice, which only the root URL reads: before the first render, `/` is replaced by `/en/` when English was stored (`resolveInitialLanguage`, `src/i18n/storage.ts`). Home is in the main chunk; the other pages are loaded with `React.lazy` on their first visit, each from its own chunk, so import them from their own folder (`../pages/Projects`), never through a barrel that would put them back in the main chunk. A Forbidden page (403) exists for content the visitor may not access. The routes sit in `RouteErrorBoundary` (`src/App`), below the header: a page that throws or whose chunk fails to load shows a translated error with a reload button, and the next navigation renders the routes again. After a navigation by link, `PageHeadingFocus` (`src/App`), inside the `Suspense` of the routes, gives the keyboard focus to the first `h1` of the new page, so every page needs one. Each route also needs an entry in `PAGES` (`src/utils/pages.ts`), which drives its metadata and the HTML file generated for it in every language at build time (`projects.html`, `en/projects.html`), with its `lang`, `og:locale`, canonical URL and `hreflang` links to its translations, rendered by `src/utils/pageHtml.ts` from the placeholders of `index.html` and the `meta` translations (`meta.noScript` fills the `<noscript>`). This is required: the build also emits a not found page per language (`404.html`, `en/404.html`, served by Cloudflare for the unknown paths of their folder), which turns off Cloudflare's single-page-app fallback, so a route without its own HTML file would return a 404 on reload. The `folder` of the entry names the page folder whose chunk that HTML file preloads (`modulepreload`), so a direct visit downloads it with the main chunk. The build also emits `sitemap.xml` (`renderSitemap`, `src/utils/sitemap.ts`), the URL of every page of `PAGES` in every language with the same translations as the `hreflang` links of its HTML file (`getPageAlternates`, `src/utils/pages.ts`), which `public/robots.txt` declares. The header shows the version of the build after the logo, `__APP_VERSION__`, which `vite.config.ts` reads from `package.json` (`define`, typed in `src/vite-env.d.ts`), and, from the tablet breakpoint, centered under the floating language toggle, a round CV button without icon (`CvLink`, `src/App/Header`, which the mobile menu shows as a pill with a download icon) then the official GitHub icon (`GitHubLink`), which the mobile menu shows under the CV button. On hover and keyboard focus, never on a tap, each CV button shows its action in its `Tooltip` (`src/App/Header/CvLink`), which also names it for screen readers (`aria-labelledby`, read even while hidden), and which `Escape` closes before the menu that holds it (`isTopLayer` of `useEscapeKey`): space a CV button from its neighbours with the `gap` of its container, since a margin on the link would move the tooltip away from it. From the tablet breakpoint, `Page` keeps the `floating-controls-room` space of the theme on its right instead of `page`, so that the floating controls cover no content: a page that sets its own right padding uses it too, as `Projects` does.

**Component conventions**: every component lives in its own folder named after it:

- `ComponentName.tsx` — the component, with JSDoc on the component and on every prop
- `ComponentName.spec.jsx` — its tests, **required** for every component, at least a render without props
- `ComponentName.styled.ts` — styled-components styles, when it has any (not documented with JSDoc)
- `index.ts` — re-export

Sub-components get the same structure in their own folder inside their parent's folder. A component shared by several sub-components of a parent sits at the root of that parent's folder. Components shared across pages live in `src/components/` (e.g. `StatusMessage`, or `Page`, the `<main>` landmark that every page extends with `styled(Page)` and a `backgroundImage` prop). A page has exactly one `<main>`, its `Page`, so nothing inside it renders another, and exactly one `h1`, visually hidden when the design shows none (as on `/projects`), with `h2` and below for its sections; each page spec checks both. Every list is a `List` (`src/components/List`), extended with `styled(List)`: a `ul` with `role="list"`, since the global style removes the bullets and Safari then stops exposing a `ul` as a list (ESLint `no-restricted-syntax` refuses `styled.ul` and `<ul>` in the other TypeScript files of `src`), and the spec of each list checks its role. A `ComponentName.styled.ts` is imported only by its own component (ESLint `no-restricted-imports` enforces it): styles shared by several sub-components go in a lowercase style module at the root of their parent (e.g. `src/pages/Experiences/timeline.styled.ts`), and styles shared by pages go in a component of `src/components/`. Props are optional by default, and components must render without crashing when a prop is missing.

**Styling and design tokens**: `src/theme/tokens.ts` holds the primitive scales (palette, spacing, sizes, font sizes…) and `src/theme/theme.ts` the semantic tokens, following the xstyled theme conventions (`colors` with `-aNN` alpha variants, `space`, `sizes`, `fontSizes`, `radii`, `shadows`, `zIndices`, `durations`, `timingFunctions`, `screens`…). Import `styled`, `css`, `keyframes`, `createGlobalStyle`, `ThemeProvider` and `th` from `@xstyled/styled-components` only, never from `styled-components` directly (ESLint and a test enforce it). Styled-components read the tokens with the `th` helpers (`th.color('accent-a55')`, `th.space(16)`, `th.radius('md')`, `th('screens.tablet')`); color names are type-checked, and `src/theme/theme.spec.jsx` checks that every token used in a style file exists. A negative space token is written `th.space(-8)`. `keyframes` have no theme context, so they read the `theme` object (`translateY(-${theme.space[12]})`), as JavaScript code (canvas, inline styles) does. A value shared with JavaScript stays a named constant, interpolated with its unit (`${BUTTON_WIDTH_PX}px`). `App` provides the `ThemeProvider` and `GlobalStyle` (which replaced `index.css`). Never write a raw color, spacing, size, font size, radius, shadow, duration, easing, z-index or breakpoint in a style file: look for an existing token first, then add one to the right scale. `theme.spec.jsx` fails on any length in `px`, `em`, `rem` or `ch`, duration, color, easing, or raw z-index, font weight or line height written in a `*.styled.ts` file or `GlobalStyle.ts` (`findRawValues`, `src/theme/testUtils.js`); zero, percentages, viewport units, angles and unitless numbers (scale factors, opacities, flex factors) may stay raw. `theme.ts` writes no value itself: each semantic token reads a primitive of `tokens.ts` (`radii[12]`, `easings.easeOutBack`, `shadowShapes['4-24']`), or a color built from one with `alphaVariants`, and `theme.spec.jsx` fails on a literal or a raw value written there (`findRawThemeValues`, same file). A new value therefore goes into a primitive scale first.

**Logic, constants and hooks**: magic numbers are named constants with their unit (`constants.ts` next to their users), computations are pure helpers in `utils.ts` with tests, and stateful effects are hooks in `hooks/useThing/` with tests (see `src/pages/Home/hooks`).

**Static data**: page-level data lives in `.data/*.json` files inside the page directory (e.g. `src/pages/Projects/.data/freelance-projects.json`). A text shown to visitors is not written there but named by a translation key, as the `nameKey` and `typeKey` of each project, translated under `projects.names` and `projects.types` by `translateProjects` (`src/pages/Projects/utils.ts`), so every language has its own; client names keep the same text in both files.

**Link preview image**: each language has its own, `public/og-image.jpg` in French and `public/og-image-en.jpg` in English (`OG_IMAGE_PATHS`, `src/utils/pages.ts`), which every page of that language names in its `og:image` (`%PAGE_IMAGE_URL%`). `pnpm og-image` (`scripts/og-image/`) generates both from the texts of the home page in each language (`TRANSLATION_MODULES`), the theme, the web fonts, the background photo and the particle field of the home page, read through Vite, with the font files of `public/fonts/` as data URLs, so it needs no network. It runs on demand: regenerate them and commit them when one of those changes. A new language needs its path in `OG_IMAGE_PATHS` and its module in `TRANSLATION_MODULES`.

**Web fonts**: the site serves its fonts itself and requests nothing from Google: never add a link to Google Fonts or to any other Google service, which `google-requests.e2e.ts` refuses. The files are in `public/fonts/`, a stable place that other scripts read (`pnpm og-image`, the generation of the CV): `montserrat-latin.woff2` (Montserrat, a variable font drawing every weight from 100 to 900) and `saira-stencil-one-latin.woff2` (Saira Stencil One, 400), the `latin` subsets that Google Fonts served to Windows and Linux, byte for byte, with their hinting, which macOS, iOS and Android ignore, next to their licenses (`montserrat-OFL.txt`, `saira-stencil-one-OFL.txt`), served with the site. `FONT_FACES` (`src/theme/constants.ts`) declares them once, and `renderFontFaces` (`src/theme/utils.ts`) writes their `@font-face` rules, with `font-display: swap`. The `font-faces` plugin of `vite.config.ts` adds to the head of `index.html`, before `page-meta` copies it into every page, a link that preloads each file, since every page shows both fonts, then a `<style>` of these rules (`getFontFaceTags`, `vite/utils.ts`). Keep the rules out of `GlobalStyle` and any styled-component: Chrome loads the fonts again each time styled-components adds a rule to its style sheet, and draws the fallback font meanwhile, which made `project-cards.e2e.ts` flaky. A script that renders a page in these fonts calls `renderFontFaces` with a `getUrl` that turns each URL into a data URL of the file, as `pnpm og-image` does. A new font needs its `woff2` file and its license in `public/fonts/`, and an entry in `FONT_FACES`: `src/theme/constants.spec.ts` checks the files and the licenses, `vite.config.spec.ts` that every generated page preloads and declares each font and names no host of Google.

**Assets**:

- Background images are served from `public/` and referenced with absolute paths (e.g. `'/projects.webp'`), always written as one whole string: the standalone build rewrites these strings into relative URLs (`'./projects.webp'`), and misses a URL built from parts (`'/' + name`)
- SVGs are imported as React components via `vite-plugin-svgr`

**Tests**: Vitest + Testing Library. Test files are co-located with the code they test: `*.spec.jsx` for components, `*.spec.ts` for helpers and hooks, `*.spec.js` for the script helpers of `scripts/ci/utils/` and `scripts/og-image/utils/` and for the JavaScript test helpers (`src/styleTestUtils.js`, `src/pages/testUtils.js`, `src/theme/testUtils.js`). `vite.config.spec.ts` builds the site in memory with the real config and checks the generated pages, such as the chunk each one preloads, and the sitemap, and `vite.standalone.config.spec.ts` does the same for the standalone build. The setup file, `src/setupTests.ts`, extends Vitest with `@testing-library/jest-dom` and wraps every `render` of Testing Library in the theme and global styles of the app (`withTheme`, `src/testUtils.tsx`), around the wrapper a spec passes, so a spec adds no `ThemeProvider` (only the specs of `src/theme` render it, to test the theme and the global styles themselves). It also gives no canvas context, and fails a test that logs with `console.error`: fix the warning (an update outside `act`, such as a page loaded with `React.lazy`, is awaited with a `findBy` query or `waitFor`), or silence an expected error with `vi.spyOn(console, 'error').mockImplementation(() => {})`. As in production, styled-components inserts each rule into the CSSOM with `insertRule` (`SC_DISABLE_SPEEDY: 'false'` in the `test.env` of `vite.config.ts`), since jsdom parses a whole `<style>` again on every change of its text, which made the suite several times slower: the `<style>` elements hold no text, so read the rules through `document.styleSheets`, with `listStyleRules` and `declaredStyle` of `src/styleTestUtils.js`, shared by the specs of every folder. `src/setupTests.ts` also fails a test whose component inserts a rule that the CSSOM refuses or that holds the source of a function (a function interpolated outside a `css` block), since browsers drop it (`logDroppedCssRules`, `src/cssRuleGuard.ts`). The CSSOM serializes a declared value as browsers do (a length of `0` as `0px`, `calc(24px - 5px)` as `calc(19px)`, `url("/a.webp")` with quotes): build an expected value from tokens with `serializeCssValue`. jsdom ignores media queries (except `all` and `screen`), does not focus an element hidden by `display: none`, converts computed lengths into pixels, and leaves out of `getComputedStyle` a rule whose selector list holds a pseudo-element (`*, *::before, *::after`): read the declared rules in those cases. jsdom decides `:focus-visible` from the last keyboard, mouse and focus events and from the last element that matched it, which it keeps for the whole file, so it refused it after the first Tab of a file: `patches/@asamuzakjp__dom-selector.patch` (`patchedDependencies` of `pnpm-workspace.yaml`) fixes its selector engine so that an element reached with Tab matches it during its focus event, where `useTooltip` reads it, whatever the tests before. Read once the Tab is over, it can still be false: check what the focus shows, such as the tooltip, rather than the pseudo-class. The patch applies to every version of the package, and the install fails when it no longer applies (`ignorePatchFailures: false`) or when jsdom stops using the package: remove it, with its lines in this file and the README, once a release that jsdom uses fixes the bug (ISF-173), and keep the Tab tests of `Tooltip.spec.jsx` and `Header.spec.jsx`, which fail without the fix. `src/setupTests.ts` runs for every spec, including the node ones: guard any DOM global it touches. When an AI agent runs Vitest, it hides the console output of the passing tests: add `--reporter=default` to see it. Components that need routing must be wrapped with `<BrowserRouter>` in tests. The helpers shared by the page tests live in `src/pages/testUtils.js`, in JavaScript like the specs, such as `isPublicFile`, which checks that an image URL names a file of `public/`.

**Browser tests**: jsdom computes no layout, so what needs one is checked in Chromium by the Playwright tests of `e2e/` (`*.e2e.ts`, `playwright.config.ts`), on the production build that `pnpm preview` serves on the port of the worktree. At the URLs of each language of `LANGUAGES` (`/projects`, `/en/projects`), at 320, 375, 414 and 1440 px, `horizontal-overflow.e2e.ts` opens every route of `PAGES` and an unknown path, and fails when a page is wider than the screen, and `timeline.e2e.ts` opens the Experiences page, and fails when the center of a dot of its timeline is more than 0.5 px from the center of the line. `google-requests.e2e.ts` opens every route of each language, and fails when a request of the page goes to a host of Google (`isGoogleUrl`, `e2e/utils.ts`: the `GOOGLE_DOMAINS` of `e2e/constants.ts` and their subdomains, and the country domains of the search engine), or unless each font of `FONT_FACES` is loaded. `language.e2e.ts` fails unless the preview server sends each page the HTML file of its language (its canonical URL), the root opens at `/en/` once English is stored, and the toggle moves a page to its English URL, which a reload keeps. The line and the dots are pseudo-elements, which the DOM gives no box for: the timeline test measures them through the DevTools protocol (`e2e/pseudo-elements.ts`), and finds them by the `data-timeline-line` and `data-timeline-dot` attributes, whose value names the pseudo-element that draws them (`before` or `after`), so keep each attribute in step with its CSS. At 375, 800, 1280, 1440, 1720 and 2400 px, `project-cards.e2e.ts` clicks "Show all" in each section of the Projects page, and fails unless the cards keep the width and height of the row, with as many per row as the row shows whole, every row starting on the left, and nothing scrolling sideways, and unless the last page of the row puts its cards in the columns of the first page. At 800, 1280, 1440 and 1920 px, `github-link.e2e.ts` fails when the CV button then the GitHub icon are not centered under the language toggle, when the CV button is not round, another one shows or a click does not download the PDF, or when they move as the page scrolls, and at 320, 375 and 414 px when the mobile menu does not show the icon centered under the CV button; at the same desktop widths, `floating-controls.e2e.ts` opens every route of each language, and fails when a text, link, button, image or icon of the page shares some width with the toggle, the CV button or the icon, so would pass under them while the page scrolls, also once every "Show all" of the Projects page is clicked. At the same desktop widths and in each language, `cv-tooltip.e2e.ts` fails unless hovering the floating CV button shows its tooltip whole on the screen, on its left at the `tooltip-gap` of the theme and centered on it, open while the pointer moves onto it, unless `Tab` shows it too and `Escape` hides it, unless the accessibility tree of Chrome names the button after its tooltip, hidden or shown, with no description (`getBrowserAccessibleText`, `e2e/accessibility.ts`), and at 320, 375 and 414 px unless the CV button of the open menu, focused with `Tab`, shows it whole above it at the same gap, under the last link of the menu, and a first `Escape` closes the tooltip but not the menu. Install the browser once with `pnpm exec playwright install --only-shell chromium`. Their helpers are tested by Vitest like any other (`e2e/utils.spec.ts`, `e2e/pseudo-elements.spec.ts`, `e2e/accessibility.spec.ts`, and `e2e/animations.spec.ts` for `waitForEndingAnimations`, which waits for the animations that end before a measure).

**CI and deployment**: `.github/workflows/ci.yml` checks formatting, lint, types (`src/`, `vite/`, `e2e/`, the configs and `scripts/`), the workflows with actionlint and ShellCheck (`workflows` job, which does not hold the deployment: a pinned actionlint version, its SHA-256 checksum checked, which Dependabot does not update, and `.github/actionlint-matcher.json` for the annotations), tests with coverage thresholds and the bundle size, builds, checks in Chromium that no page of the build scrolls sideways or requests Google, that the timeline dots sit on its line, that each page is served at its URL in each language (`/en/…`), that the CV button and the GitHub icon sit centered under the language toggle, the icon under the CV button of the mobile menu, and that no content passes under them, that the tooltip of the CV button shows whole next to it, and that the project cards keep their size and their columns, in "Show all" and on the last page of the row (browser-test job, Chromium cached per Playwright version), then deploys the `dist` artifact to Cloudflare Pages (project `issoufi-fr`) with Wrangler and smoke-tests it: `main` goes to production at issoufi.fr, any other branch to a preview, and on `main` it also checks that `http://issoufi.fr/` and `https://www.issoufi.fr/` redirect to `https://issoufi.fr/` (`check-redirects.mjs`). On pull requests, it also checks the commit messages with commitlint (except Dependabot's) and runs GitHub's dependency review. Cloudflare's own automatic builds are paused. `.github/workflows/deploy-production.yml` puts `develop` in production every morning at 6:00, Paris time: of its two crons (`0 4 * * *` in summer, `0 5 * * *` in winter, kept equal to `DEPLOY_CRON_BY_UTC_OFFSET_MINUTES` of `scripts/ci/constants.mjs` by a test), only the one of the day's offset goes on (`check-deploy-schedule.mjs`). Its `release` job first makes the release of the day, with no one involved (`merge-release-pr.mjs`): it finds the release pull request (label `autorelease: pending`), runs `ci.yml` on its branch by hand (`workflow_dispatch`) and waits for it, merges it at the tested commit once that whole run passed, then starts `release.yml` and `ci.yml` on `develop` and waits for that CI. GitHub holds the workflows of a pull request opened by GitHub Actions until a person approves them, and a merge made with the `GITHUB_TOKEN` starts no push run, while a run started by hand starts at once: so it needs no secret. The job never fails the deploy (a notice, or a warning, when no release can be made), and its `GITHUB_TOKEN` alone may write (`contents`, `pull-requests`, `actions`). The `check` job then stops with a notice when the trees of `main` and `develop` are the same, or unless the last run of `ci.yml` on `develop` for that exact commit succeeded, started by a push or by the release (`check-develop-ci.mjs`), and fails when the `DEPLOY_KEY` secret is missing. Otherwise it merges that commit into `main` with a merge commit (`chore: deploy develop to production`), fails unless the result has the tree of the tested commit, and pushes it with the deploy key: unlike the `GITHUB_TOKEN`, that push starts the CI on `main`, which deploys production. A `workflow_dispatch` runs it at once, and its `dry_run` input runs the CI of the release pull request without merging it, and merges into `main` without pushing (`git push --dry-run`); its job summary lists the commits deployed (`write-deploy-report.mjs`). Being scheduled, it only runs from the default branch, `develop`. `.github/workflows/rebuild.yml` reruns the CI on `main` on the first day of every month, so the years of experience written in the HTML files stay right, and `release.yml`, which the daily release also starts by hand after its merge (`workflow_dispatch`), maintains the release-please pull request and, when merging it creates a release, attaches the standalone build to it (`issoufi.fr-v<version>.zip`). That build (`vite.standalone.config.ts`) takes the production config as it is, with a relative base and the dynamic imports inlined, and adds plugins: the app inlined in the script tag of `index.html` (`inlineScript`, without the `__VITE_PRELOAD__` markers that Vite leaves, `removePreloadMarkers`), the `HashRouter` in place of `BrowserRouter` for the imports of `react-router` from `src/` (`vite/standalone/react-router.ts`), relative URLs for the files of `public/`, the font files of `FONT_FACES` embedded as data URLs in the `@font-face` rules of the page, without the links that preload them, and no other HTML page; its helpers are in `vite/standalone/utils/`, one file per topic, each with its tests. Never make `vite.config.ts` or the app depend on it. The helpers of the CI scripts are in `scripts/ci/utils/`, one file per topic (`annotations.mjs`, `bundle.mjs`, `bundle-report.mjs`, `coverage.mjs`, `deploy-report.mjs`, `github-api.mjs`, `html.mjs`, `pages.mjs`, `job-summary.mjs`, `lists.mjs`, `numbers.mjs`, `redirects.mjs`, `release-pull-request.mjs`, `schedule.mjs`, `step-output.mjs`, `workflow-runs.mjs`), each with its tests.

## Conventions

- **Branches**: `main` is production, `develop` the integration and default branch. Two rulesets, _Protect develop_ (25318593, no bypass) and _Protect main (daily deploy from develop)_ (25335502), refuse direct pushes, force pushes and deletions: every change goes through a pull request with passing checks. The one exception is `main`, updated every morning by `deploy-production.yml`, which pushes its merge of `develop` with the read-write deploy key _Daily production deploy_ (private key in the `DEPLOY_KEY` secret), the only bypass actor of the ruleset of `main`. The site owner manages the key, the secret and the rulesets: never change them. Work on each ticket in its own Worktrunk worktree, on a branch named after the ticket reference (`ISF-35`, from the `ISF-` autolink to the issues). Start it with the `ticket-worktree` skill (`ticket.mjs start ISF-35`), which fetches `develop` and branches from `origin/develop`, rather than with a bare `wt switch --create`. Open its pull request against `develop` with `Closes #35`. No pull request targets `main`, not even for a release: `develop` reaches it every morning once its CI passed, so a change merged into `develop` is in production the next day.
- **Ports**: when a worktree is created, `.config/wt.toml` writes `PORT=<port>` to its `.env.local`, a port derived from the branch (10000–19999). `vite.config.ts` reads it with `getServerPorts` (`vite/utils.ts`) for both `pnpm dev` and `pnpm preview`, and `playwright.config.ts` for the preview server of `pnpm test:browser`, so read a worktree's port in its `.env.local` rather than assuming 3000. Without `PORT`, as in the main checkout, they use 3000 and 4173. A taken port stops the server with an error (`strictPort`) instead of moving it to another port, and `BROWSER=none` stops Vite from opening the browser.
- **Commits**: Conventional Commits enforced via commitlint + husky (`feat:`, `fix:`, `refactor:`, etc.). They set the next version and `CHANGELOG.md`, which release-please writes: never edit the changelog by hand, and use `feat`/`fix` only for changes a visitor of the site would notice, since those appear in it.
- **Formatting and linting**: on commit, lint-staged runs `eslint --fix` then Prettier on staged files, one after the other (`--concurrent false`, as both write the same files). A lint error stops the commit.
